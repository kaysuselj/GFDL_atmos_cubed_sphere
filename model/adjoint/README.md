# Discrete TL/AD of the FV3 tracer advection (GCHP 14.8.0), standalone test builds

Option B of `FULL_ADVECTION_ADJOINT_SCOPE.md` (devkit `adv_adjoint_devkit_C24/docs`): the exact
transpose of the linear scheme `hord_tr = 2`, `kord_tr = 17`, with the mass fixer either frozen
(s = s0) or linearized. The TL and AD are generated by TAF from the **unmodified** forward files
`../tp_core.F90`, `../fv_tracer2d.F90`, `../fv_mapz.F90`, `../fv_fill.F90`.

Two builds of the same generated code: one face on one process (no MPI), and the six cube faces on
6 or 24 MPI ranks with FMS and GCHP's halo exchange.

## Layout

| path | content |
|---|---|
| `stubs/stubs.F90` | stand-ins for FMS and the FV3 modules the forward files use, as TAF sees them. The communication goes through three external black-box routines with TAF flow directives (top of the file): `adj_halo_q` (q halo update), `adj_global_sum` (mass-fixer sums), `adj_reduce_max` (Courant max). The C-grid wind halos are passive data. |
| `comm/adj_comm_single.F90` | back-end for one face: the halo update is the identity (or a copy of stored neighbour values, for the forward check), sums are the identity |
| `comm/adj_comm_fms.F90`, `comm/fv_arrays_fms.F90` | back-end for six faces: the real `fv_mp_mod` (`domain_decomp`, `start/complete_group_halo_update`), FMS `mpp_update_domains_ad` as the halo adjoint, `mpp_sum`, `mp_reduce_max`, and the C-grid wind halos by the `mpp_get_boundary`/`mpp_update_domains` calls of `offline_tracer_advection` |
| `fms/build_fms.py` | builds the needed part of geoschem/FMS 259759d1 standalone (GCHP's fms_r4 definitions) |
| `prep/make_face_inputs.py` | one face and one step of a devkit trajectory (`traj/<case>`) → raw r8 files: grid metrics with halo, CX/CY/MFX/MFY with halo (rotated from the neighbouring faces), dry pressure edges, q, ak/bk |
| `driver/adj_face_mod.F90` | the passive inputs of the step (grid, winds, pressures) for this rank |
| `driver/adj_load.F90` | fills `adj_face_mod` from the prep files (one face, or this rank's subdomain of its face); not seen by TAF |
| `driver/adj_tops.F90` | the differentiated top-level `top_adv(mode, ...)`: `top_tp2d` (fv_tp_2d, one level), `top_tracer2d` (tracer_2d), `top_step` (the full step of `offline_tracer_advection`: q halo update, tracer_2d, map1_q2, mass fixer) |
| `driver/test_fwd.F90` | one face: forward vs GCHP (hord 12 / kord 8); `top_step` = `offline_tracer_advection` |
| `driver/test_adv.F90` | dot-product and TL-vs-FD tests of one step (one face or six faces) |
| `driver/test_halo.F90` | six faces: dot test of the q halo update and its adjoint alone |
| `driver/test_chain.F90` | six faces: N steps, J = q at receptor cells (P2a format), FD vs adjoint vs TL |
| `taf/run_taf.sh` | regenerates `taf/gen/` with the TAF server (`staf`) |
| `taf/map1_q2_structured.F90` | GOTO-free `map1_q2`, substituted only in the TAF input copy (see below) |
| `taf/gen/` | TAF output: the forward modules again, plus the `_tl` and `_ad` routines. `taf.log` is the TAF log; `fv_mapz_tafinput.f90` is the exact fv_mapz input given to TAF |
| `taf/gen_gchp/` | the TAF output as GCHP compiles it: all modules renamed (`stb_*`, `adj_*`), lines ≤ 132 columns (`tools/make_gen_gchp.py`, run by `run_taf.sh`) |
| `gchp/adv_adj_discrete.F90` | the adapter between GCHP (AdvCore) and the generated code: init from GCHP's real gridstruct/flags/domain, one adjoint step, one forward step, convention check |
| `gchp/sources.cmake`, `gchp/patches/` | the GCHP build (fvdycore CMake include) and the AdvCore patch (`ADV_ADJ_METHOD: discrete_linear`) |
| `gchp/HANDOFF_PLEIADES.md` | how to apply, build and validate in GCHP (task 4) |
| `driver/test_gchp_adapter.F90` | the adapter in a GCHP-like build (real fv_arrays.F90 / fv_mp_mod.F90, gen_gchp) |
| `tools/compare_decomp.py` | compares the per-rank fields of two decompositions |
| `tools/check_conventions.py` | compares the advection inputs of an adjoint run with those of the forward run (GCHP output) |
| `run_tests.sh` | one face: prep + both tests for a list of cases |
| `results/` | test outputs referred to in STATUS.md |

## Build and run

```bash
make                     # build/test_fwd (original forward), build_ad/test_adv (TAF code), one face
python3 prep/make_face_inputs.py --traj <devkit>/traj/8ms --face 4 --step 1 --out <work>/8ms_f4_s01
build/test_fwd <work>/8ms_f4_s01            # forward vs GCHP (hord 12 / kord 8)
build_ad/test_adv <work>/8ms_f4_s01         # TL/AD tests, hord 2 / kord 17 (pass: ALL TESTS PASSED)
./run_tests.sh <devkit>/traj <work> "8ms 4 1" "tiltedrot 3 10" "merra2 5 12"

# six faces (FMS, MPI); prep all faces into <dir>/f1..f6, run where an input.nml (fms_nml) is
python3 fms/build_fms.py <FMS source> <FMS build>          # once; make mpi FMSB=<FMS build>
make mpi
mpirun -n 6  build_mpi/test_halo 1                         # layout 1: one rank per face
mpirun -n 24 build_mpi/test_adv <dir> 2 17 2 [wind_scale]  # layout 2: 2 x 2 ranks per face
mpirun -n 24 build_mpi/test_chain <chain dir> 48 <receptors.txt> 2   # <chain dir>/sNN/f1..f6
make gchp                                                  # the adapter, GCHP-like build
mpirun -n 6 build_gchp/test_gchp_adapter <dir> 1

taf/run_taf.sh           # regenerate taf/gen after changing a differentiated routine
```

Compiler: gfortran, `-fdefault-real-8 -fdefault-double-8` (FV3 runs in r8), with GCHP's fvdycore
definitions `-DMAPL_MODE -DSPMD -DTIMING`. MPI: MPICH. The six-face build compiles the stub modules
under other names (`-Dmpp_mod=stb_mpp_mod`, ...), so that the real FMS and `fv_mp_mod` link
alongside.

## What TAF gets, and why

TAF differentiates `top_adv` with `-forward -reverse` (TL and AD in one run, so that both are in
the same generated modules), `-r8 -f08 -N 512`. It differentiates `top_step`, not
`offline_tracer_advection` itself. In reverse mode TAF cannot handle the reuse of the `xL/yL`
buffers for CX and MFX there, nor the GOTOs of the unused `mapn_tracer` path. `top_step` repeats
the glue code of `offline_tracer_advection` and calls the unmodified `tracer_2d` and `map1_q2`. It
is bit-identical to `offline_tracer_advection` at -O0 (test_fwd prints the check).

The fv_mapz copy that goes to TAF has two changes, made by `run_taf.sh`; the repository file is
unchanged:
- `map1_q2` is replaced by `taf/map1_q2_structured.F90`: the same arithmetic with flags instead of
  GOTOs. The GOTOs make the control-flow graph irreducible, and TAF then loses the q1 → q2
  dependence.
- `ppm_limiters` declares `dm(itot)`, `a4(4,itot)` in place of the assumed-size `dm(*)`,
  `a4(4,*)`, because TAF cannot store assumed-size arrays. This path is used only for kord ≤ 7.

The forward of the TAF build is bit-identical to the original build (test_fwd and test_adv both
write `step_*` files into the data directory).

`run_taf.sh` post-processes and checks the generated code in two places:
- the adjoint of q in `start_halo_4d_ad` is made `intent(inout)`. TAF declares it `intent(in)`,
  although the black-box adjoint overwrites it;
- the calls of the black boxes are checked against the argument lists of the back-ends. The calls
  go through implicit interfaces, so the compiler would not catch a change.

TAF pitfalls met on the way:
- a conditional overwrite of array elements inside loops over the whole array is taken as a kill
  of the array. A blend `w*q + (1-w)*h` keeps the dependence;
- top-level routines must be external subroutines, not module procedures;
- a black-box adjoint (`ADNAME`) gets only the active arguments unless `DEPEND` lists the others;
- a module variable that is both read and assigned from an active value becomes active, and its
  TL/AD copy carries over between calls. Hence `adj_s0` (read) and `adj_s_last` (written).
