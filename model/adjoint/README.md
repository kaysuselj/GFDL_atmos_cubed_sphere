# Discrete TL/AD of the FV3 tracer advection (GCHP 14.8.0), single-face test build

Option B of `FULL_ADVECTION_ADJOINT_SCOPE.md` (devkit `adv_adjoint_devkit_C24/docs`): the exact
transpose of the linear scheme `hord_tr = 2`, `kord_tr = 17`, with the mass fixer either frozen
(s = s0) or linearized. The TL and AD are generated by TAF from the **unmodified** forward files
`../tp_core.F90`, `../fv_tracer2d.F90`, `../fv_mapz.F90`, `../fv_fill.F90`.

This is the single-face build (one process, no FMS/MPI). The q halo is an input of the test
operators, or zero. The halo exchange across faces and its adjoint come next (task 2, with FMS).

## Layout

| path | content |
|---|---|
| `stubs/stubs.F90` | single-face stand-ins for FMS and the FV3 modules the forward files use. Halo exchanges of q are no-ops, or copy a stored halo. The C-grid wind halos come from the neighbouring faces (passive). `mpp_sum` is the identity. |
| `prep/make_face_inputs.py` | one face and one step of a devkit trajectory (`traj/<case>`) → raw r8 files: grid metrics with halo, CX/CY/MFX/MFY with halo (rotated from the neighbouring faces), dry pressure edges, q, ak/bk |
| `driver/adj_face_mod.F90` | loads those files (grid, winds, pressures) |
| `driver/adj_tops.F90` | the differentiated top-level `top_adv(mode, ...)`: `top_tp2d` (fv_tp_2d, one level), `top_tracer2d` (tracer_2d), `top_step` (the full step of `offline_tracer_advection`: tracer_2d, map1_q2, mass fixer) |
| `driver/test_fwd.F90` | forward check against GCHP (hord 12 / kord 8). Also checks `top_step` = `offline_tracer_advection` |
| `driver/test_adv.F90` | dot-product and TL-vs-FD tests of the generated TL/AD |
| `taf/run_taf.sh` | regenerates `taf/gen/` with the TAF server (`staf`) |
| `taf/map1_q2_structured.F90` | GOTO-free `map1_q2`, substituted only in the TAF input copy (see below) |
| `taf/gen/` | TAF output: the forward modules again, plus the `_tl` and `_ad` routines. `taf.log` is the TAF log; `fv_mapz_tafinput.f90` is the exact fv_mapz input given to TAF |
| `run_tests.sh` | prep + both tests for a list of cases |

## Build and run

```bash
make                     # build/test_fwd (original forward) and build_ad/test_adv (TAF code)
python3 prep/make_face_inputs.py --traj <devkit>/traj/8ms --face 4 --step 1 --out <work>/8ms_f4_s01
build/test_fwd <work>/8ms_f4_s01            # forward vs GCHP (hord 12 / kord 8)
build_ad/test_adv <work>/8ms_f4_s01         # TL/AD tests, hord 2 / kord 17 (pass: ALL TESTS PASSED)
./run_tests.sh <devkit>/traj <work> "8ms 4 1" "tiltedrot 3 10" "merra2 5 12"
taf/run_taf.sh           # regenerate taf/gen after changing a differentiated routine
```

Compiler: gfortran, `-fdefault-real-8 -fdefault-double-8` (FV3 runs in r8).

## What TAF gets, and why

TAF differentiates `top_adv` with `-forward -reverse` (TL and AD in one run, so that both are in
the same generated modules), `-r8 -f08 -N 512`. It differentiates `top_step`, not
`offline_tracer_advection` itself. In reverse mode TAF cannot handle the reuse of the `xL/yL`
buffers for CX and MFX there, nor the GOTOs of the unused `mapn_tracer` path. `top_step` repeats
the glue code of `offline_tracer_advection` and calls the unmodified `tracer_2d` and `map1_q2`. It
is bit-identical to `offline_tracer_advection` at -O0 (test_fwd prints the check).

The fv_mapz copy that goes to TAF has two changes, made by `run_taf.sh`; the repository file is
unchanged:
- `map1_q2` is replaced by `taf/map1_q2_structured.F90`: the same arithmetic with flags instead of
  GOTOs. The GOTOs make the control-flow graph irreducible, and TAF then loses the q1 → q2
  dependence.
- `ppm_limiters` declares `dm(itot)`, `a4(4,itot)` in place of the assumed-size `dm(*)`,
  `a4(4,*)`, because TAF cannot store assumed-size arrays. This path is used only for kord ≤ 7.

The forward of the TAF build is bit-identical to the original build (test_fwd and test_adv both
write `step_*.r8` into the data directory).

Two TAF pitfalls met on the way:
- a conditional overwrite of array elements inside loops over the whole array is taken as a kill
  of the array. That is why the q-halo stub uses a blend (`stubs.F90`, `start_halo_4d`);
- top-level routines must be external subroutines, not module procedures.
